# Cyberboss 稳定基线

这份基线定义 Cyberboss 在 2026-08-25 恢复后的可接受状态。它不是当前
实现细节的快照，而是后续修改不得悄悄破坏的行为边界。

## 一、主聊天

1. 同一微信会话复用唯一的主 runtime binding 和 thread/session。
2. 普通后续消息不得创建新 Claude 进程、后台 binding 或隐式新线程。
3. `/new` 是唯一显式新会话边界；新线程不得自动灌入时间轴、工作日志、
   日记或无界连续包。
4. 新线程恢复以 Ombré 记忆和有限可见对话为主。读取日记、时间轴和工作
   日志必须由当前请求需要驱动，并限定范围。
5. 用户补充消息可以 live steer 当前主 turn；内部 check-in 必须让位于用户
   消息，不能接收用户文本作为内部 turn 的 steering。
6. 主聊天不得静默失败、重复终局回复或在上一条终局消息尚未确认投递时
   启动下一轮。

## 二、进程与线程所有权

1. 正常驻留态只有一个 Cyberboss 主进程、一个主 Claude 进程和它的项目
   MCP 子进程。
2. 日记、时间轴、check-in 和 finalize 不拥有长期 Claude 会话，也不能把
   session id 写入主 binding 或彼此的 binding。
3. 重启可以 resume 已有主 thread，但不得恢复 `::background:*` binding。
4. 后台模块失败、超时或被限额时只能结束自己的 run，不能关闭、污染或
   重建主聊天线程。

## 三、Token 与工具边界

1. 冷启动允许一次 prompt cache miss；稳定后新增输入应保持增量，不能每轮
   重灌完整历史。缓存读取量和新增输入量必须分开报告。
2. 普通闲聊新线程的恢复工具最多 2 次、硬上限 60k Token；显式工作任务可
   使用普通工具，但保留 250k 紧急上限。
3. main check-in 为零工具 turn、硬上限 60k Token；前置观察只能走受限、
   只读 NCP。
4. 后台每项工作必须有独立 task/source、调用次数、Token 上限、超时和可查
   usage 记录。不得用完整 Claude 进程代替一次模型调用。
5. 简单问候不得因为“恢复状态”无界搜索工具、工作日志、时间轴和日记。

## 四、Check-in、日记和时间轴

1. Check-in 小模型只做廉价 gate 和任务建议，不能以 CC 身份生成可见消息。
2. 最终的联系、沉默或私人日记由现有主 CC thread 决定。沉默是自由判断，
   不是默认，也没有固定夜间静默规则。
3. Garden/社交观察为可选的受限只读 NCP 任务，主线程拥有最终决定权。
4. 增量日记和时间轴是独立、幂等、可恢复的一次模型任务；空增量不调用
   模型。正式收尾每天执行一次，并保持既有格式。
5. 投递成功后才更新 check-in 的已发送计数和退避；待投递状态跨重启保存。

## 五、上线与回滚门槛

跨越 runtime、binding/session、turn lifecycle、投递、后台调度或模型预算中
任意两项的改动，视为高风险架构变更。开始前必须写明：

- 要改变的边界和明确不改变的边界；
- 最坏故障模式，包括新线程、重复进程、无界读取、重复投递和后台烧 Token；
- 对应的失败回归测试；
- 单独的上线步骤和回滚点。

上线前运行：

```bash
npm run baseline:check
```

该命令必须完整通过，不得通过削弱断言、删除测试或扩大默认预算来“修复”
失败。重启必须单独获得 uu 授权并使用：

```bash
./scripts/restart-now.sh
```

重启后只读核对：服务健康、单主 Claude、主 thread 未变、投递队列为空、
最近日志无循环/连续失败，并观察至少一轮相关真实行为。禁止为了验收主动发送
付费测试消息，除非 uu 明确要求。
